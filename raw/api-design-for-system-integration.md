# Own the record, share the reference, evolve independently

Make one system the owner of each piece of data, give each record a permanent opaque ID issued by that owner, publish a small versioned contract, and let every other system keep only that ID plus the few fields it needs. For your example, system A owns A1 and issues its ID. System B stores `a1_id` as a foreign reference and may cache a copy of selected fields, but it never edits that copy and never reads A's database. Changes travel from A to B as events (with a read API for on-demand lookups and for catching up), and every hop assumes duplicates and out-of-order delivery. Independence comes from five habits: publish a contract separate from A's internal model, only add to that contract, make B's apply logic idempotent and version-guarded, translate A's model into B's at B's edge, and never share a database. The ownership and identifier rules in the first section come from established practice and were not verified against sources in this research. The reliability and versioning rules are mostly backed by primary documentation. The integration-style trade-offs are also not source-verified. A "Confidence and gaps" section near the end shows which is which.

## One owner, one opaque ID, and consumers keep only a reference

*Not source-verified. This section reflects well-established practice (domain-driven design, system-of-record thinking), written from background knowledge. No fetched source supports it.*

The "same reference" problem is solved by ownership, not by a shared model. Pick a **system of record** for each entity: the one system allowed to create and change it. Everyone else holds a derived copy. The owner issues an **immutable, opaque identifier** (a UUID or similar). Immutable means it never changes or gets reused. Opaque means it carries no meaning, so it cannot contain a name, a department, or a national ID number that later changes or leaks. Business keys such as an employee number can be exposed as attributes, but they should not be the join key between systems.

A consumer stores the foreign ID and only the fields it needs to do its own job. It treats those fields as a read-only cache of the owner's data. If B needs a field to be authoritative, B should own that field itself and A should not duplicate it. Each system keeps its own model of the concept. A translation layer (an anti-corruption layer) at B's edge converts A's published shape into B's internal shape, so A's vocabulary does not leak into B. The alternative, one enterprise-wide canonical data model that every system must conform to, is widely criticised because it couples everyone to one model and one change process. Prefer a small, domain-scoped published model per owner instead. The integration-styles research note makes the same argument, but its text is entirely unverified.

## Pick the loosest integration style that meets the freshness need

*Not source-verified. The source note for this section was written from recollection of canonical sources (Enterprise Integration Patterns, Fowler, Newman, microservices.io) because fetching was blocked. Treat it as expert background, not as cited findings.*

Shared-database integration is the style to rule out first. It makes A's schema a public contract, so every internal change becomes a cross-team change. Beyond that, the practical choice follows what B needs. If B needs an answer right now, call A's synchronous API (REST or gRPC) with timeouts and a circuit breaker, accepting that B depends on A being up. If B must react to changes or keep a local copy, use events. If the consumer is an external organisation, use webhooks with signatures, retries and a list endpoint for reconciliation. If the need is bulk or analytical, use batch files or a governed data product, and keep that interface separate from the operational one.

Events come in two shapes. A thin "notification" event carries only the ID and the type of change, so B calls back to A for details. That keeps A authoritative and lets A check authorisation on every read, but B still cannot finish its work when A is down. A fat "state transfer" event carries the fields consumers need, so B runs without calling A, at the cost of a wider contract, duplicated data and eventual consistency. For HR data, the sensible split is a fat event for non-sensitive attributes (name, unit, position, status) and a thin event plus authorised read for sensitive ones (salary, personal identifiers). That split is a reasoned recommendation, not a sourced claim. In either case, keep a read API alongside the events so B can recover from missed messages.

## Reliability: assume duplicates, disorder and deletion

Across independent systems, plan for at-least-once delivery and make the receiver idempotent. Kafka's own documentation describes the levels: at-most-once can lose messages, at-least-once loses none but can duplicate (the default), and exactly-once is real only where state and consumer offsets commit together, such as Kafka-to-Kafka pipelines ([Confluent](https://docs.confluent.io/kafka/design/delivery-semantics.md)). The same page warns that many systems claim exactly-once without accounting for failures outside the system. The practical consequence is that A and B, as separate systems, should not rely on exactly-once delivery.

On the producing side, use the **transactional outbox**. A writes the business change and an outbox row in one local database transaction, and a separate relay publishes the row. This gives "sent if and only if committed" without a distributed transaction. The relay can crash after publishing and before marking the row, so it can publish twice, and consumers must therefore be idempotent ([microservices.io](https://microservices.io/patterns/data/transactional-outbox)). On the consuming side, B should store the processed event ID, or the entity ID plus version, in the same transaction as the change it applies. That is the same "commit state with offset" idea Confluent describes, applied to a relational consumer (this adaptation is an inference). Write APIs that accept retries should follow the Idempotency-Key convention used by Stripe: the client generates a high-entropy key, the server stores the first result (including errors), and a retry with the same key returns that stored result ([Stripe](https://docs.stripe.com/idempotency)). The IETF header draft formalising this, with 400, 409 and 422 error semantics, expired in April 2026 and is not a standard, so document your own policy and treat the draft only as a naming convention ([IETF draft](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header)).

Ordering and deletion need explicit design. Carry a monotonic version with every change and apply an event only if its version is higher than the stored one; ignore equal versions as duplicates and stale ones as late. Partition events by the entity's ID so per-entity order holds, since global order is not needed. For optimistic concurrency on write APIs, HTTP ETags with `If-Match` return 412 on a mismatch, and the client should refetch and reconcile instead of retrying blindly ([Ed-Fi guide](https://docs.ed-fi.org/reference/data-exchange/api-guidelines/design-and-implementation-guidelines/api-implementation-guidelines/handling-optimistic-concurrency-with-etags)). Model deletes as explicit events (a versioned "deleted" flag), not by absence. A null-value tombstone in a compacted Kafka log signals that all earlier records for the key may be removed, so it does not protect a late-joining consumer ([Debezium](https://debezium.io/documentation/reference/3.0/transformations/event-flattening.html)). A retained delete marker with a version also stops a stale update from resurrecting a deleted record (inference). For multi-step workflows that span systems, sagas use local transactions plus compensations. Compensations can fail, and steps after the "pivot" must be retryable and idempotent ([Azure Saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)).

## Contracts: write the spec first, only add to it, and say what unknown means

Treat the contract as a product owned by A. Major API style guides require contract-first design: Zalando mandates writing and reviewing the OpenAPI spec before implementing, and publishing it ([Zalando](https://opensource.zalando.com/restful-api-guidelines/)). OpenAPI is at version 3.2.0 (September 2025) ([OpenAPI Initiative](https://www.openapis.org/tag/overlay)). For events, Avro, Protobuf or JSON Schema in a schema registry enforces compatibility. Confluent's modes show the trade-off: BACKWARD (the default, checked only against the latest version) needs consumers upgraded before producers; FORWARD needs producers first; **FULL lets either side upgrade in any order** ([Confluent](https://docs.confluent.io/platform/8.1/schema-registry/fundamentals/schema-evolution.html)). FULL, and the TRANSITIVE variants when old data is retained or replayed, best match the goal of independent release cycles (the recommendation to prefer TRANSITIVE is an inference; Confluent defines the term without recommending it). The format split (OpenAPI for request/response, a registry for events) is a common heuristic, not a sourced rule.

Change rules are consistent across the guides read. Adding fields, endpoints and enum values is safe. Removing, renaming or retyping fields, changing resource names, changing value formats or defaults, and adding new required fields are breaking ([Google AIP-180](https://google.aip.dev/180)). Zalando adds that consumers must accept compatible extensions and treat enums as open-ended, so A can add a new value without breaking B ([Zalando](https://opensource.zalando.com/restful-api-guidelines/)). On the consumer side, Fowler's Tolerant Reader says to read only the fields you need, ignore the rest, and parse in one place ([Fowler](https://martinfowler.com/bliki/TolerantReader.html)). The IAB's RFC 9413 pushes back on blanket tolerance, arguing that silently accepting faulty input is almost always wrong ([RFC 9413](https://datatracker.ietf.org/doc/rfc9413/notprepped/)). The workable resolution, which is my inference, is to ignore unknown additive fields and unknown enum values by a rule written into the contract, but to fail loudly on missing or malformed required data.

Because additions are cheap and removals are breaking, expose the minimum set of A1 fields at first. Anything exposed and relied on is effectively permanent, and Google warns that even undocumented behaviour counts ([Google AIP-180](https://google.aip.dev/180)). Keep the published model separate from A's database or domain model so internal refactoring does not change the wire shape (inference). Versioning guidance conflicts, and the conflict is real. Google puts a major version in the URL path (`/v1/`) and never exposes minor versions ([AIP-185](https://google.aip.dev/185)). Zalando forbids URL versioning, prefers avoiding versions altogether, and uses media-type versioning only for incompatible changes ([Zalando](https://opensource.zalando.com/restful-api-guidelines/)). Stripe pins each account to a date-based version and transforms responses backward ([Stripe, 2017](https://stripe.com/th-de/blog/api-versioning)). For two internal systems, additive change within one major version, with a new major version only for a truly incompatible change, is enough (inference). Signal retirement with the `Deprecation` header (RFC 9745) and the `Sunset` header (RFC 8594); both are hints, so clients must work without them ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html)). Use `application/problem+json` for errors ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)), and cursor pagination with opaque cursors for list endpoints ([Zalando](https://opensource.zalando.com/restful-api-guidelines/)).

To catch breaking changes before release, consumer-driven contract tests (Pact) record what B actually uses and replay it against A, and a `can-i-deploy` check gates the release. The sources here are secondary. Pact's own documentation could not be fetched, and the same guide lists event-driven systems as a poor fit for classic Pact. PactFlow's bi-directional variant, which compares A's OpenAPI spec with B's recorded usage, is lighter and fits cases with many or unknown consumers, but gives weaker guarantees ([PactFlow](https://docs.pactflow.io/docs/bi-directional-contract-testing)). With one producer and one known consumer, classic Pact is viable; with more consumers, spec diffing in CI is simpler (inference).

## Security and governance travel with the data

The OWASP API Security Top 10 (2023) is a sound checklist, and three entries bear directly on a system holding a copy of someone else's data. API1 is broken object-level authorisation, API3 is broken object-property-level authorisation, and API10 is unsafe consumption of APIs ([apisecurity.io](https://apisecurity.io/owasp-api-security-top-10/)). Read as design rules (inference), A should scope the fields each consumer can see so B's copy holds only what it needs, B should validate A's payloads instead of trusting them, and an inventory of interfaces and versions covers API9. Idempotency keys must be high-entropy and cached under a composite key, so one client cannot read another's cached response ([IETF draft](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header)). Personal-data erasure is the HR-specific consequence of replicated copies: when A deletes or anonymises an employee, the delete event must reach every consumer's copy. The research found no source on the legal requirements (Indonesia's UU PDP, GDPR), so confirm them with legal counsel.

## Recommendation: an employee record owned by one system, used by others

Assume an HR Core system owns the **Employee** entity, and Payroll, Attendance and the Org-chart service consume it. This is a design proposal assembled from the practices above, and the field names are illustrative.

First, HR Core assigns each employee an `employee_id` (a UUID) at creation. It never changes, never gets reused, and encodes nothing. The human-facing `employee_number` is an ordinary attribute. Second, HR Core publishes an OpenAPI contract with `GET /v1/employees/{employee_id}` and a cursor-paginated `GET /v1/employees?updated_after=...` for catch-up. It also publishes an `employee.changed` event, including `employee_id`, a monotonic `version`, a `status` (including `terminated` as an explicit state), and the non-sensitive fields consumers need (display name, unit ID, position ID, employment status). The event schema sits in a registry with FULL_TRANSITIVE compatibility. Salary and national ID are not in the event; Payroll reads them from an authorised endpoint. Third, HR Core writes the event to an outbox in the same transaction as the change.

Each consumer keeps a table keyed by its own primary key, with `employee_id` as a unique foreign reference, a `source_version`, and only the cached fields it needs. On each event it checks the event ID or `source_version`, applies it only when the version is newer, and commits that in one transaction. It ignores unknown fields and unknown enum values, and rejects malformed required fields. Consumers never write to the cached fields. Payroll's own concepts (pay grade, tax status) live in Payroll, keyed to the same `employee_id`; they are not added to HR Core's contract. Each consumer translates HR Core's shape into its own model in one adapter class, so a change in HR Core touches one file. A scheduled job compares counts or hashes per range against HR Core's list endpoint and repairs gaps by re-fetching (standard practice but unsourced here). A new consumer, or a rebuild, bootstraps from the list endpoint and then switches to events, using the same idempotent apply path for both.

In HR Core's release pipeline, a contract check blocks removals, renames, retypings and new required fields. When a field must go, mark it deprecated in the spec, add `Deprecation` and `Sunset` headers, watch usage until it reaches zero, and only then remove it.

## Conclusion

The most useful result is a division of labour, not a technology choice. Ownership and identity are decisions to make once, per entity, and independence is bought by keeping A's model private behind a small contract, while B protects its own model at its boundary. Every technique in the verified material (outbox, idempotent apply, versions, additive-only change) exists to make that boundary survive failure and time.

Two points remain open. The versioning guides disagree, so the choice between path versions and media-type versions is a team convention, not a correctness issue. And the least-evidenced part of this research (ownership, identifiers, thin vs fat events) is the part your HR design depends on most, so verify it first.
